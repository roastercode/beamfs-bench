## Diagnostic conclusions

### Confirmed working

- The beamfs-bench v0.8.0 -> emufi 0.3.2 debugfs forwarding chain works
  for numeric and bool entries : `multi_segment`, `width_mode`,
  `multi_chip`, `chip_count`, `target_struct`, `codeword_size_bytes`,
  `codeword_align_bytes` were all visible in the kernel snapshot at the
  expected values.
- emufi SEU single-bit injection works deterministically : 7 then 6
  flips with the expected ratio against `skipped_filter + skipped_prob`.

### Confirmed broken

1. **flip_locality string vs int** -- worker.sh pushed the string
   `EXACT` to the debugfs entry (which is `debugfs_create_file_unsafe`
   with custom `emufi_..._fops`), the kernel kept value 1 (CONSECUTIVE).
   Either the parser silently rejects non-numeric input, or it parses
   `EXACT` as 0 and we inherited 1 from defaults. **Either way, pushing
   a string instead of an int is a bug in the v0.8.0 contract.**
   The v0.7.8 release notes quick-start used `FLIP_LOCALITY=4` (numeric)
   for this exact reason.

### Strongly suspected broken

2. **MBU bursting never fires** -- `flip_count_mbu_w*` stayed at 0 in
   both runs, even with `multi_segment=Y + width_mode=1 +
   burst_symbols=9 + multi_chip=Y + chip_count=4`. Either there is a
   third condition not yet pushed (e.g. the kernel needs `flip_locality
   = EXACT = 4` to gate burst emission, which run #2 missed because of
   bug #1 above), or there is an actual bug in the kernel-side burst
   emission path.

### Honest assessment of why no corruption was observed

- Target file = 3 KB = 12 codewords RS(255,239). At prob=1M ppm with 7
  flips total over 24576 bits, expected corruption is ~0.6 bits per
  codeword. RS(255,239) corrects t=8 errors per codeword. **The
  experiment is two orders of magnitude under-dimensioned to saturate
  RS.**
- Even a fully working MBU bursting emission would not have changed
  this conclusion : the file is too small, the targeting is too coarse,
  the trial count is 1.
- emufi behaves correctly within its scope. **The harness is the
  bottleneck**, not the injector.

## Action items for next session (priority order)

### P0 - Diagnose MBU bursting (must come before anything else)

Read `~/git/emufi/src/emufi-0.2.0/emufi_main.c` and
`emufi_hooks_blk.c`, locate the burst emission decision path (likely

Optional : add a kunit test in emufi that asserts `width_mode=1 +
multi_segment=1 + burst_symbols=9 + flip_locality=EXACT` produces a

### P1 - Fix flip_locality integer/string handling

Two acceptable fixes :

(a) **Rust-side**, in `src/main.rs` `EmufiAttackArgs::export_to_env`,
    convert the string to its integer encoding before calling
    `std::env::set_var` :
```rust
if let Some(v) = self.flip_locality.as_ref() {
    let int_val = match v.to_uppercase().as_str() {
        "RANDOM"      => "0",
        "CONSECUTIVE" => "1",
        "EXACT"       => "4",
        s if s.parse::<u8>().is_ok() => s,  // already numeric
        _ => return Err(...)  // hard reject unknown tokens
    };
    std::env::set_var("FLIP_LOCALITY", int_val);
}
```

(b) **Bash-side**, in `src/worker.sh` attack action :
```bash
case "${FLIP_LOCALITY:-}" in
    RANDOM)      v=0 ;;
    CONSECUTIVE) v=1 ;;
    EXACT)       v=4 ;;
    *)           v="${FLIP_LOCALITY}" ;;  # numeric passthrough
esac
echo "$v" | sudo tee ${INJECTOR_DBG}/flip_locality >/dev/null
```

Preferred : (a). String-to-int conversion belongs in the typed CLI
layer, not in shell. Bash should only ever push numeric values to
debugfs.

Lockstep : the same bug class probably affects no other entry today
(all other custom-fops entries in emufi accept numeric values).

### P2 - Variable target file size

Current setup hardcodes 3 KB files (`head -c 3072 /dev/urandom`) in
3 dirs of 3 files each. Change to a parametrizable size. Suggested :

- Add CLI flag `--target-file-size-mb` (default 4) in main.rs, exported
  via `TARGET_FILE_MB` env var.
- worker.sh setup honors `${TARGET_FILE_MB:-4}` and adjusts `head -c`
  accordingly.
- 4 MB = 16384 codewords RS(255,239), enough volume for statistically
  meaningful saturation observations.

### P3 - Codeword-precise targeting

To run the **theorem IV.1 saturation regime** test, we need to put
exactly t+1 = 9 errors **inside one specific codeword**, not 9 errors
distributed randomly over a file. Steps :

1. After populating the target file, run `filefrag -e` on it to obtain
   the physical block extent on the device.
2. Pick a codeword inside : codeword index k -> byte offset = k *
   `codeword_size_bytes` (= 255), block-aligned to 4096.
3. Push `target_block` = the block containing the codeword,
   `target_struct_offset` = the byte offset inside the block,
   `flip_locality=EXACT`, `burst_symbols=9`. The injector will then
   place all 9 flips contiguously at the chosen offset.

This requires worker.sh to learn the filefrag arithmetic. Estimated
effort : ~50 LOC bash + a few lines in cluster.rs to plumb the new
env var (`TARGET_CODEWORD_INDEX` or similar).

### P4 - Statistical multi-trial loop

Single-shot per (FS, prob) is insufficient to observe a saturation
regime that has any probabilistic component. Run N=10 attacks per
(FS, prob, codeword), aggregate verdicts, report frequency of
RECOVERED / UNCORRECTABLE / UNDETECTED. Already half-supported by the
existing `probs = [1000, 100000, 1000000]` loop -- generalize to a
`(prob, trials)` matrix.

### P5 - Forensics dump completeness

The compute01 injector-counters.log printed by the bench did NOT
include `burst_symbols` in either run, even though the kernel has the
debugfs entry (verified at module-load via grep
`debugfs_create_u8 ("burst_symbols",...)` in emufi_main.c). The
`forensics.rs` Rust path that dumps `/sys/kernel/debug/emufi/*` should
be audited -- it likely iterates `ls` output and may hit a perm
boundary or a hardcoded allowlist.
